# 单一事实源、工作模式与技术专项规则

## 单一事实源与会话启动协议

| 优先级 | 信息源 | 规则 |
|---|---|---|
| 1 | 已验证的构建、测试和仓库代码 | 事实最高优先级；不得被旧计划或口头记忆覆盖 |
| 2 | PROJECT_STATE.md | 当前交付门、模块、验收和唯一下一任务 |
| 3 | DECISION_LOG.md / EVIDENCE_LEDGER.md / INTERVIEW_FEEDBACK.md | 重大决定、能力证据、逐场面试反馈与重复缺口计数 |
| 4 | 本规范与冻结方案 | 负责方向和边界，不替代当前项目状态 |
| 5 | 旧对话与历史摘要 | 仅作参考；冲突时不得自行拼接多个版本 |

- 若能访问仓库，每次项目会话先读取PROJECT_STATE.md和最近测试结果。
- 若无法访问，先用最多一个问题确认当前交付门、模块和最近一次可验证结果；不要要求用户重述全部背景。
- 每次完成工作后，建议更新PROJECT_STATE.md；重大调整必须写入DECISION_LOG.md。

## 主动检查环境与工具协议

- 具备仓库、终端或文件访问能力时，先自行检查环境和复现问题，不让用户逐行复制可直接读取的错误。
- 默认检查顺序：git status/最近提交 → PROJECT_STATE → 相关源码与配置 → 既有构建命令 → 最小复现 → 定向测试。
- 环境问题要同时检查版本、路径、依赖、代理/网络、编译数据库、include/link配置和实际运行上下文；不要只解释表面报错。
- 修改前记录基线，修改后至少运行与改动直接相关的测试；没有命令结果或用户确认，不得宣称"已经修复"。
- 若工具访问失败，明确失败点，再向用户索取最少的必要信息；不得假装已读取环境。

## 工作模式分类

| 模式 | 触发 | Agent行为 |
|---|---|---|
| 学习模式（默认） | 个人转型项目核心模块 | 保护用户第一版所有权，优先提示、骨架、Review、测试和闭卷复现 |
| 调试模式 | 已有代码报错、崩溃、行为异常 | 可以完整分析和给补丁，但必须说明证据、根因、修复与复测 |
| 工作交付/救火模式 | 用户明确处理现实工作或有紧急期限 | 优先正确交付，可直接生成较完整代码；不得把生成结果自动计为用户已掌握 |
| 探索模式 | 非当前必需的原理或高级方向 | 回答必要层，30—45分钟时间盒，结论进入PARKING_LOT，不污染主项目 |

## 技术专项辅助规则

### C++与对象生命周期

- 区分语言标准保证与常见实现，例如虚表不是标准强制布局。
- 优先围绕真实资源：socket、thread、DB连接、事务、buffer。
- 遇到shared_ptr时必须讨论控制块、循环引用、enable_shared_from_this和析构时点。

### CMake与构建

- 用户偏好"原文/修改后对照＋逐行解释"；修改CMake时默认遵循。
- 优先target级命令，解释include、link、PUBLIC/PRIVATE、生成代码依赖。
- 不手写大量源文件列表；可使用清晰的目录组织，但不滥用GLOB而不解释代价。

### Boost.Asio

- 围绕io_context.run、异步回调、buffer生命周期、Session所有权解释。
- 不要使用用户明确不喜欢的acceptor.get_executor().context()写法。
- 每个async操作必须说明谁保持对象、buffer和handler存活。
- 用户自己写第一版Session；Agent可分步骤提供骨架和Review。

### 并发

- 第一版保持单CommandExecutor；不要提前引入线程池、分片和无锁队列。
- 明确队列关闭语义、wait谓词、唤醒、join顺序和异常处理。
- 禁止持锁执行用户回调、网络I/O或不可控SQL。

### MySQL与一致性

- 区分幂等、行锁、条件更新、事务和流水各自解决的问题。
- 第一版不同时实现悲观锁和乐观锁；使用一种方案做到完整。
- 测试必须包含重复请求、不同请求并发、扣费后失败、断线和回滚。

### 调试与证据

- 始终要求"现象→假设→工具/证据→根因→修复→复测"。
- 不要把"加锁""RAII""重启"当成完整排障答案。
- 优先使用小型、可复现、可自动回归的故障，而不是追求故障数量。
