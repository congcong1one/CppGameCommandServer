# AI时代工程训练质量系统

本文件规定“如何训练”，不增加技术栈或新的并行课程。目标是在每周6—8小时内，把一次完成转化为能够保持、迁移和借助Agent放大的工程能力。

## 世界级AI原生工程师的七维能力

| 能力维度 | 可观察行为 | 本项目主要证据 |
|---|---|---|
| 问题定义 | 把模糊需求变成约束、非目标、风险和完成标准 | 场景说明、测试预言、任务简报 |
| 系统建模 | 画清状态、所有权、线程、数据流和失败传播 | 状态转换、所有权/线程图、关键不变量 |
| 工程实现 | 用最小闭环稳定交付可读、可改、可测试的实现 | 渐进Diff、构建测试、边界处理 |
| 证据与排障 | 从现象提出假设，用工具定位根因并回归 | 最小复现、日志/调试器/Sanitizer、Bug记录 |
| 生产所有权 | 考虑运行、观测、停止、故障、安全和回滚 | build/run/stop、故障演练、恢复说明 |
| AI协作判断 | 按风险委派，审完整Diff，纠正Agent并验证结果 | AI等级、拒绝/改写、硬验证、校准记录 |
| 学习与表达 | 快速获得一手证据，把模型迁移到陌生变体并清楚说明取舍 | 延迟迁移、技术口述、复盘与外部反馈 |

不是每张卡都同时训练七维。任务卡只选2—4个主维度，但一个Gate结束时必须有覆盖其核心维度的证据，不能用代码量或工具熟练度代替。

## 一张高质量任务卡的闭环

1. **能力靶心**：写“完成后能做什么”，不用“学完哪些名词”代替。
2. **轻量诊断**：用一个真实行为预测、代码阅读或最小操作确定已有模型；不先做长问卷。
3. **真实场景**：说明对象、平台、约束、失败后果和为什么生产中在意。
4. **最小理论与支架**：只提供当前实验所需模型、API契约和易错点；支架按需要给，不按固定教学脚本灌输。
5. **预测与行动**：用户在运行前留下一个可证伪预测，再实现、调试或Review最小增量。
6. **硬证据**：运行构建、测试、系统调用、日志、调试器或Sanitizer，不以“看起来正确”验收。
7. **三行自解释**：只记录“原预测 / 实际证据 / 模型改变”，不写应试式长答案。
8. **反馈与再试**：Agent先诊断错误类别，只处理当前最高杠杆问题；用户用下一次行动验证修正。
9. **支架撤除**：一旦能独立完成当前层，下一增量减少提示，不长期停留在示例模仿。
10. **延迟迁移**：24—72小时后用10—15分钟陌生变体、缺陷Diff或简化重建重新调用该模型；优先嵌入后续任务，不制造独立作业债务。

即时通过证明“这次做成”，延迟迁移才开始证明“形成能力”。延迟检查失败不否定此前努力，也不清空其他证据；把模块局部降一级，用一次最小修复循环恢复。

## 自适应支架梯度

Agent必须选择当前所需的最低一档支架，并在成功后撤除：

| 档位 | Agent提供 | 适用条件 |
|---|---|---|
| S0 独立尝试 | 场景、完成标准、硬验证入口 | 用户已有足够前置模型 |
| S1 定向线索 | 指出应观察的状态、契约或一个关键问题 | 方向偏离但仍能自行推进 |
| S2 对比支架 | 非目标实现的微型对比例、状态轨迹、部分完成示例，并要求用户自解释差异 | 同一模型错误重复两次或任务元素过多 |
| S3 局部骨架 | 接口/测试骨架、关键API位置、可运行最小复现；关键判断仍留给用户 | 语法/工具负担遮蔽核心概念 |
| S4 共同修复 | Agent给局部补丁并逐项验证，用户解释和重做简化版 | 已有首版、进入AI-1调试，或安全风险不适合盲试 |

- AI-0不等于“什么都不教”。Agent可以提供理论、对比例和局部骨架，但不能直接交付当前核心目标的完整可复制实现。
- 不把“长时间卡住”浪漫化。独立尝试约20—30分钟仍没有新证据，或同一种模型错误连续出现两次，就升级一档支架。
- 如果用户首轮正确且能解释，不补更多基础题；用一个更真实的迁移变体替代重复练习。
- 支架围绕任务难点变化：C++概念已懂但Linux API未知时直接给API契约；API会用但所有权模型错误时用状态轨迹；模型正确但实现报错时进入真实调试。

## 反馈诊断与带宽控制

Review前先把当前主要障碍归为一类：

| 类别 | 典型信号 | Agent优先动作 |
|---|---|---|
| M 心智模型 | 预测与运行行为系统性相反 | 给状态轨迹或对比例，再做一个最小实验 |
| K 知识/API | 不知道稳定契约、版本或工具入口 | 直接给最小理论和一手资料定位，不让用户盲搜 |
| I 实现 | 模型正确，但代码的分支、生命周期或边界写错 | 指向最小Diff和失败用例，让用户修复 |
| E 证据/工具 | 只凭日志或感觉，测试不能证明结论 | 改造观察点、断言、调试器或Sanitizer验证 |
| A Agent监督 | 能运行但没有审Diff、风险判断或残余风险 | 先做风险排序，再审关键不变量和测试缺口 |
| P 过程/范围 | 一次改太多、目标漂移、无法最小复现 | 缩小增量、恢复单一假设和停止条件 |

一次反馈默认只给一个会改变正确性、安全性或后续理解的最高杠杆问题。当前层通过后，才能处理第二层的可维护性、命名或风格；不得用十几条意见淹没因果关系。

## 保持与迁移，不做机械复习

- **即时层**：当前实验行为正确，用户能解释预测差异。
- **延迟层**：24—72小时后不看原实现，读一个缺陷Diff、补一个局部空白、重建核心状态转换或设计验证。
- **迁移层**：7—14天内在后续真实模块重用同一模型，例如从文件描述符所有权迁移到线程、Session或事务生命周期。
- 不固定每天背卡片，不重复原题原答案。延迟任务必须换表面情境，仍验证同一个底层模型。
- 延迟检查优先占用下一张卡的前10分钟；每周总投入不因此增加。

## AI时代的“双循环”

### 能力形成循环

用于新的核心概念：AI提供理论、概念澄清、验证入口和分级支架；用户拥有预测、关键判断、首版和第一次排障。重点训练代码阅读、调试和概念模型，而不是只训练语法回忆。

### 杠杆交付循环

用于已形成最低能力的领域：用户定义目标、约束、风险和测试预言；Agent执行更大范围实现；用户按风险审Diff、纠正Agent、运行硬验证并准备回滚。重点训练“让Agent做更多，同时让系统风险更可控”。

每个核心模块先经过能力形成循环，再尽快在后续真实工作中进入杠杆交付循环；两者不是两门分离课程。

## AI判断校准

AI原生能力不能只记录“用了Agent”，还要比较预期与实际：

1. 委派前用一句话预测：AI会节省什么、最大风险在哪、哪项证据决定完成。
2. 看测试前先指出Diff中最可疑的一处或最可能缺失的失败路径。
3. 验证后记录：预期收益是否出现、风险是否命中、还剩什么无法由现有证据排除。
4. 每个核心模块最多保留一条校准记录；不记录冗长Prompt和聊天流水。

主观“很快”“几乎没Bug”不是校准。只有与无AI基线、任务耗时、Review发现、返工、测试或生产结果相比较，才形成证据。模型能力快速变化时重测任务边界，不把某一版本的效率结论永久化。

## 方法证据与适用边界

- [Anthropic 2026随机实验：AI辅助与编码技能形成](https://www.anthropic.com/research/AI-assistance-coding-skills)：52名以初级为主的开发者学习陌生Python库时，AI组即时掌握度较低，最大差距出现在调试；概念性询问并独立编码与较高表现相关。样本小、评估时间短，支持“新概念保留认知投入”，不能推出所有生产任务都应少用AI。
- [Anthropic 2026约40万次Agent编码会话分析](https://www.anthropic.com/research/claude-code-expertise?level=0)：更强任务领域知识与更高成功/恢复相关，典型分工偏向人做规划、Agent做执行。它是观察性且大量指标由分类器推断，只用于支持领域模型和可验证目标的重要性，不作因果或薪资结论。
- [Shin等2023编程实验](https://doi.org/10.1177/07356331231174454)：126名本科生的三周实验中，渐退式worked example结合元认知支架表现最好。适用于“必要时先支架、随后撤除”，不支持给用户复制当前任务的完整答案。
- [Chi等1989自解释研究](https://doi.org/10.1207/s15516709cog1302_1)：学习者把例子步骤与原理连接、监控理解偏差时，更能形成不依赖例子的知识。研究领域是力学题，因此本方案只迁移其“三行自解释”机制，并用工程实验验证。
- [Karpicke与Blunt 2011提取练习实验](https://pubmed.ncbi.nlm.nih.gov/21252317/)：提取练习促进科学材料的概念学习和推理。这里把它改造成延迟代码阅读、排错和重建，不据此恢复机械口试。
- [METR 2026开发者生产率实验更新](https://metr.org/blog/2026-02-24-uplift-update/)：后续研究因Agent普及、多Agent并行和任务选择产生明显测量偏差，无法可靠估计统一效率倍数。它支持按具体任务持续校准AI收益，不支持任何固定“AI提速/减速”结论。

教育研究多来自学生、短期实验或非编程领域；AI研究也受模型版本和工具形态限制。因此这些原则是当前最佳工作假设，最终仍以用户在本项目中的构建、调试、迁移和真实投递/工作反馈迭代。
