# 面试反馈记录与路由协议

## 记录规则

- 仓库可能公开：公司、面试官和商业项目使用不可反推的代号；不记录联系方式、邀请链接、精确地点、原始简历文件或其他身份线索。
- 每场面试只记录事实：原问题、用户回答、追问、明确反馈、结果和可验证证据；不要根据情绪重构整个计划。
- 统一分类：C++基础、算法、Linux、网络、数据库/一致性、项目表达、商业C++硬门槛、岗位不匹配。
- 第二场独立面试出现同类缺口时才标记为"重复缺口"；随后用强化包替换当前低优先级任务。

## 漏斗检查

- 若10次定向投递几乎无面试，优先检查简历、岗位层级、地区和薪资，不通过继续堆项目功能解决。
- 若技术交流尚可但持续因无商业C++被拒，应明确个人项目边际收益下降，扩大真实C++过渡岗。

## 交付门C：反馈路由表

| 反馈 | Agent应如何调整 |
|---|---|
| 数据库追问多 | 补MySQL事务、request_id、FOR UPDATE、条件扣费、流水和回滚测试 |
| 基础题失败 | 暂停扩展，增加闭卷与反例；不要用更多项目功能掩盖基础 |
| 算法失败 | 建立限时算法专项，主项目只维护 |
| Linux弱 | 加入core dump、gdb、系统工具和故障报告 |
| 只缺商业C++ | 停止功能扩张，扩大过渡岗位；个人项目的边际收益已下降 |
| 实时岗位要求高 | 启动独立RealtimeLoopLab，不污染主项目 |
| 大型代码库质疑 | 做一次现有C++仓库构建、调用链、补丁和测试 |

## 投递节奏提醒

- Gate A完成后：安排低优先级校准面试，阻止"再准备一点"。
- Gate B达标后：开始主要投递，不把MySQL作为前置门槛；投递过程中默认补MySQL事务。
- Gate B完成后、至少10次定向投递或2场技术面试前：只允许修Bug、补测试、补文档和练口述。
- 每10次投递检查漏斗；两次重复缺口才路由强化方向（替换，不追加）。
