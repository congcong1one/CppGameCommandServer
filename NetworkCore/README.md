## 构建

Python 测试客户端及连接、发收、分段发送示例见 [tools/README.md](tools/README.md)。客户端默认连接 `127.0.0.1:9981`，支持原始字节和当前 18 字节帧协议。

在仓库根目录执行：

```bash
cmake -S NetworkCore -B NetworkCore/build -DCMAKE_BUILD_TYPE=Debug
cmake --build NetworkCore/build --parallel 1
./NetworkCore/build/NetworkCoreDemo
```

VS Code 应打开 `NetworkCore/` 文件夹。保存构建脚本和 F5 配置仍在 `.vscode/`，调试程序改为 `build/NetworkCoreDemo`。

## 公共层的目标边界

| 部分 | 合适的职责 | 应留给服务业务的职责 |
|---|---|---|
| Transport | socket、连接生命周期、异步读写、收发缓冲、发送队列、容量限制与关闭通知 | 玩家、登录状态、数据库操作 |
| Protocol | 帧头、长度校验、完整帧编码解码；按需提供独立 Protobuf 适配 | 具体消息的业务处理与身份授权 |
| Runtime | I/O 执行环境及回调在哪个线程执行的约定 | 游戏命令执行、数据库任务调度 |

整个通信包可以包含这几部分，但不需要全部放进 `TcpConnection`。Protobuf 可以是协议适配层的依赖；MySQL、Redis 不应成为纯 TCP 连接层的必需依赖。先沿用一个 I/O 线程验证生命周期，当前没有增加线程池或多服务部署。

## 结构与职责问题（直接说明）

结构问题直接诊断和讨论，不作为自主复现题：

- **网络连接依赖玩家业务。** `TcpConnection.hpp` 包含 `PlayerManager.hpp`，保存玩家与管理器，执行绑定和离线；`Player` 反过来保存连接弱引用。连接层宜只管理字节收发和连接生命周期，通过消息/关闭通知交给服务层处理玩家绑定。具体服务可以有自己的业务 Session。
- **基础数据类型放错了依赖层级。** `Buffer` 和 `PacketHeader` 定义在连接头文件，导致 `Tool.hpp` 为读取字节而引入连接、Asio 和玩家管理器。缓冲区类型宜独立，帧结构与编解码放协议部分，让连接使用这些基础类型。
- **帧头与消息体概念混在一起。** `PacketHeader` 包含 `body`，实际表达的是整个包；可将其命名为 `Packet`，或把固定头部与消息体分开。其中 `playerId` 是应用协议选择，不是通用 TCP 属性。
- **公共网络目标依赖过重。** `GameServer::Dependencies` 统一引入 MySQL、Redis、Protobuf。纯网络部分宜只依赖它实际使用的网络/运行时库；Protobuf 归可选协议适配，数据库连接库归需要它们的服务。
- **连接集合由文件级全局变量持有。** `connections` 和 ID 计数器没有归属到具体服务或运行时对象，多个监听实例会共享状态，停止时谁移除和释放连接也不明确。宜明确由哪个对象管理它们及其生命周期。
- **公共库形态尚未建立。** 当前只有 `NetworkCoreDemo` 入口目标。真正提取时需要可链接的库目标，把演示入口留在独立目标；同时将实际网络源码纳入编译。`network` 的可用接口、发送接口、消息回调与执行线程约定仍未完成。

这些建议尚未实施；本次只做用户要求的重命名。拆包算法、收发与关闭行为仍由用户主写和修复。

## 2026-09-21 审查：尚未修复的问题

1. **网络源码未进入构建。** `CMakeLists.txt` 只有 `src/main.cpp`。单独编译 `src/network/network.cpp` 失败：构造连接只传 socket 和 ID，而构造函数还要求 `PlayerManager&`。另行链接连接和玩家源码时，`PlayerManager::getOnlinePlayer(int)` 缺少定义。公共库提取前需要先解决这些错误，再让实际网络源码参与构建。
2. **接收链没有启动，也没有调用解析。** `network` 的构造函数、`init()`、`doAccept()` 都是私有；连接没有公开启动入口，接受连接后只存入表；`doRead()` 只再次发起读取，没有调用 `resumeBuffer()`。当前缺少从监听到消息交付的完整路径。
3. **包解析有确定的错误。** `Tool::readRingBufferUint16()` 将高字节左移后又转换成 `uint8_t`，丢掉高位；临时探针读取 `FC CD` 得到 `0x00CD`。`resumeBuffer()` 只确认有 18 字节头部，随后消费头部，却不等待完整 body；`readRingBuffer()` 不检查有效字节数。临时探针在仅有 1 个有效字节时读取 2 字节，得到 `size == -1`。完整帧到齐前应保持读取位置和有效长度不变。另有容量不一致：实际缓冲区是 8 KiB，允许 body 达到 16 KiB，`MAX_SAVE_BUFFER_SIZE` 为 32 KiB 却未使用，其注释也不正确。
4. **关闭与释放不完整。** 未绑定玩家时调用 `closeConnection()` 会解引用空 `_player`；读错误分支没有统一清理；全局 `connections` 持有强引用却没有移除路径。关闭 socket 并不等于连接对象能析构。以上为源码审查发现，尚未进行网络运行验证。
5. **公共头文件存在多编译单元问题。** `Tool.hpp` 在头文件中定义非 `inline` 的普通函数，两个编译单元同时包含时会链接重复定义，已用临时探针复现。`network.hpp` 也缺少防重复包含措施。

本次只执行重命名和审查，保留原有行为；以上缺陷没有因更名而修复。下一次代码调整可先确定 `TcpConnection` 与玩家业务的边界，以便解决构造依赖并把真实网络源码加入构建。
