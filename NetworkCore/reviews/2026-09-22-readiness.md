# 2026-09-22 网络层接入准备度审查

结论：职责骨架已形成，但还没有可运行、可验收的收发与关闭流程，当前不能认定只差 Protobuf。先完成实际网络入口与原始字节收发，再验证拆帧，最后把完整 body 交给 Protobuf 解码。本次只做审查和临时验证，未修改功能源码。

## 已形成的结构

- `doRead()`、`doWrite()` 都位于 `TcpConnection`。
- 发送使用 `deque<vector<char>>`，当前写操作成功完成后移除队首并继续下一项。
- `Buffer` 与不含 body 的 `PacketHeader` 已移到独立头文件。
- 连接构造函数已取消 `PlayerManager&` 参数，关闭逻辑不再直接处理玩家离线。
- 管理器保存 `shared_ptr<TcpConnection>`。接受连接处虽然仍使用 `make_unique`，但移交给接收 `shared_ptr` 的接口时发生合法的所有权转换；不能再把该路径直接判定为仅有 unique_ptr 所有权。
- 当前 CMake 已注释数据库依赖聚合目标；真实功能尚未因此得到验证。

## 当前结构缺口（直接说明）

1. 正式 CMake 仍只有 `src/main.cpp`，main 没有构造监听对象或启动网络操作。`network` 的构造函数和方法默认私有，`TcpConnection` 没有对外的启动、发送入口，接受连接后只登记。需要先明确可调用的启动流程。
2. 收到字节后只存入缓冲区并继续读，尚未调用拆帧流程；拆帧处尚未交付完整 body。协议层包含帧边界处理与消息体解码，Protobuf 只负责后者。
3. 发送队列缺少入队接口、容量上限及“当前是否正在写”的入口约束；需要保证无数据时不启动写、有写操作时只入队而不再启动第二个写操作。
4. 关闭没有通知管理器移除连接的接口，服务停止与连接释放的责任尚未接通。暂时保持一个 I/O 线程即可，不把分桶视为线程安全的证明。

## 功能问题：先复现，后看原因

| 场景 | 预期 | 当前证据 |
|---|---|---|
| 真正创建并销毁一个连接管理器 | 编译链接通过 | 临时生命周期探针链接失败；空入口构建不会覆盖此场景 |
| 读取字节 `FC CD` | 得到 `0xFCCD` | 实际 `0xFFCD`；UBSan 失败 |
| 读取字节 `12 34 80 01` | 得到 `0x12348001` | 实际 `0xFFFF8001` |
| 相同帧一次到达、分两次到达、两帧连续到达 | 消息内容和交付次数一致；不完整帧保持有效数据 | 源码审查发现消费位置与完整性判断存在问题，尚未运行完整拆帧场景 |
| 按连接自己的 ID 添加、移除，再释放外部引用 | 表内不再持有连接，对象可以析构 | 源码审查发现保存与查找身份不一致；尚未做运行验证 |
| 客户端断开、连续发送、写中关闭 | 统一关闭、最终释放；有序发送且内存有界 | 当前没有完整调用入口，尚未做实际 TCP 验收 |

本轮只先处理“真实网络源码进入构建并启动原始字节收发”这一项，不同时扩展 Protobuf、分桶并发或线程池。

<summary>诊断与复核依据（自主定位后再展开）</summary>

- 管理器生命周期探针只包含 `TcpConnectionManager.hpp` 并在 main 创建局部 `TcpConnectionManager`。与 `TcpConnectionManager.cpp` 一起链接，报告 `undefined reference to TcpConnectionManager::~TcpConnectionManager()`；析构函数只有声明。
- `Tool.hpp` 当前直接让可能为负的 char 参与移位或扩大转换。Ubuntu 本次编译环境下，`FC CD` 得到 `FFCD`，`12 34 80 01` 得到 `FFFF8001`；UBSan 报告 `left shift of negative value -4`。原来的高位截断改动没有解决有符号字节问题。
- `resumeBuffer()` 读取 magic 与 length 时已经消耗了 6 字节，却仍拿剩余 size 与完整头部长度加 body 长度比较。即使一整个帧已经到达，仍可能提前返回，而且下次从已推进的位置重新解析头部。body 消费与交付也尚未实现。
- `network::doAccept()` 先分配连接 ID，而管理器的 `addConnection()` 再分别生成 ID 来计算桶和键，`removeConnection()` 又按传入 ID 计算桶；三者并不一致。管理器对桶的增删也没有同步；不能据 ID 生成时加锁就声明支持多线程。
- 读错误回调没有进入关闭/移除流程；`closeConnection()` 只关闭 socket 并设置标记，没有释放管理器的强引用路径。
- `doWrite()` 当前直接访问队首，依赖调用方保证非空；缺少明确的入队入口与写中状态约束。目前尚无实际调用路径，因此没有宣称已复现空队列访问或重叠写。
